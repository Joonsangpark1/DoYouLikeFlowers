# 꽃순이 60초 꽃 잡기 챌린지 V4 — ITB104

기준: 업로드한 DoYouLikeFlowers-main.zip (fe9f9d57b1e79e64f747640770b9d0ff8145f424). 기존 코드 수정 없음. 이전 버전 exhibition_game이 있다면 백업하고 이 폴더로 교체한다. 기존 pad_map.json은 유지 가능. 기존 안전 설정은 현장 재검증 후 옮긴다.

## 먼저 게임 화면만 확인하기 (게임패드/로봇 없이 가능)

압축을 푼 `exhibition_game` 폴더에서 Python 3.10 이상으로 다음 명령을 실행한다. Windows PowerShell 또는 WSL 모두 가능.

```bash
python flower_game.py --ui-test
```

브라우저에서 http://localhost:8091 접속. 닉네임 입력 → 도전 시작 → 3, 2, 1, START! → 0부터 올라가는 타이머 → 진행자 성공 판정 → 우측 TOP 3 갱신 → 다음 참가자 순서로 체험한다. 이 모드는 실제 로봇을 연결하지 않으며 게임패드 없이도 동작한다. F11로 전체화면 표시 가능. 화면 테스트 기록은 실제 기록과 다른 DB에 저장한다. 기존 서버가 켜져 있으면 먼저 종료한다(Ctrl+C).

## V4 업데이트: 참가자 조작 연습

기존 V3 서버를 Ctrl+C로 종료하고 새 `flower_game.py`, `index.html`을 기존 폴더에 덮어쓴다. 기존 `pad_map.json`, 현장 검증한 `safety.json`, DB를 유지한다. 테스트 파일과 설명서는 선택적으로 교체한다. V3 DB 구조를 그대로 사용한다.

- 참가 준비 화면에서 **조작 연습 →** 을 누른다. 닉네임 입력 전에도 연습할 수 있다. 이미 입력한 내용은 같은 브라우저에서 연습 후 돌아올 때 유지된다.
- 실제 게임패드 입력으로 R1, 왼쪽 스틱 4방향, 오른쪽 스틱 4방향, L2/R2, SELECT를 총 12단계 연습한다. 각 이동/그리퍼 단계는 R1과 함께 조작해야 하고 입력을 약 0.25초 유지한다. 다음 단계에서는 모든 버튼과 스틱을 놓았다가 다시 조작한다.
- 현재 목표 버튼은 오른쪽 패드 그림에서 점선 테두리로 표시되고, 실제 입력은 기존처럼 노란색으로 강조된다. 왼쪽에 조작 방법, 실제 동작 의미, 진행 상황이 나타난다.
- 연습은 서버의 PRACTICE 단계에서 수행한다. 실제 REAL 모드에서도 연습 중 이동 명령을 보내지 않는다. 단, 전원이 연결된 로봇은 토크를 유지할 수 있으므로 로봇에 손을 대지 않는다. 물리적 비상정지와 감독은 계속 필요하다.
- 연습 중에는 타이머가 돌지 않고 DB 도전 기록도 생성하지 않는다. SELECT는 연습의 마지막 입력 과제로 사용하고, 화면의 정지 요청 버튼은 연습을 종료한다. 실제 도전 중 SELECT는 기존처럼 정지한다.
- 연결이 끊기면 현재 단계에서 입력 대기 상태로 돌아간다. 브라우저 연결이 끊기거나 다른 탭으로 이동하면 연습을 종료한다. 연습을 건너뛰거나 완료한 뒤 참가 등록으로 돌아갈 수 있다. 연습은 선택사항이며 참가자별 완료 내역은 저장하지 않는다.
- `--ui-test`에서만 테스트용 입력 흉내 버튼으로 단계를 넘겨 볼 수 있다. DEMO/REAL에서는 이 버튼이 없고 실제 게임패드 입력을 사용한다. 이 기능은 게임패드 없이 실제 입력을 검증했다는 뜻은 아니다.
- DEMO: 기존 PowerShell 송신기와 별도 PowerShell에서 `python flower_game.py` 실행. REAL: 기존 WSL 환경 및 안전 검증 후 `python flower_game.py --real --confirm-supervisor` 실행. 기존 게임/순위 기능은 유지한다.

## V3부터 유지되는 이틀 운영 기능

1. 기존 PowerShell/WSL 게임 서버를 Ctrl+C로 종료한다.
2. 기존 `exhibition_game` 폴더를 백업하고 새 ZIP의 파일을 복사한다. V2에서 이미 동작한다면 `flower_game.py`와 `index.html` 두 파일만 교체해도 된다. `pad_map.json`, 현장 검증을 완료한 기존 `safety.json`은 유지한다. Python 3.10 이상이 필요하다.
3. 이전과 동일하게 `python flower_game.py --ui-test`로 확인한다. 브라우저에서 `http://localhost:8091/`을 직접 입력한다. URL 뒤의 추적용 쿼리 문자열도 이제 정상 처리한다.
4. 터미널의 `ADMIN PIN (this session only):` 뒤에 표시된 8자리 PIN을 기록한다. 재실행하면 새 PIN이 발급된다. 관람객에게 보여 주지 않는다.

오른쪽 순위표의 `1일차 | 2일차 | 전체` 탭은 조회 전용이다. 현재 등록 일차는 순위표 아래의 `기록 등록: ...일차`로 확인한다. 첫 실행 시 1일차이며, 마지막 운영 일차는 재실행 후에도 유지된다. 전시 날짜가 확정되지 않았으므로 달력 기준 자동 변경은 하지 않는다.

- 첫째 날: 관리자 설정 → PIN 입력 → 1일차로 운영.
- 둘째 날: 관리자 설정 → PIN 입력 → 2일차로 운영. 1일차 기록을 삭제할 필요가 없다.
- 2일차에 1일차 순위를 보고 있더라도 새로운 기록은 2일차에 저장된다. 일차는 참가 시작 시 확정되며, 진행 중 변경은 금지된다.
- 전체 탭: 양일의 성공 기록 중 가장 빠른 순으로 TOP 3 표시.
- 기록 관리: 관리자 설정 → PIN 입력 → 범위 선택(1일차/2일차/전체) → 기록 조회(50개씩) / CSV 내보내기 / 선택 범위 초기화. 개별 기록을 삭제할 수도 있다. 전체 초기화에는 DELETE 입력 확인이 필요하다(일차별 초기화도 동일). 삭제 후 복원 기능은 없으므로 필요시 먼저 CSV를 저장한다. CSV는 담당자 전용이며 연락처가 포함될 수 있다. 관리자 PIN 검증은 서버에서 수행하며 연속 5회 실패 시 30초 제한한다. 로컬 전시 운영용 보호장치이지 다중 사용자 보안 시스템은 아니다. 운영 PC를 관람객에게 맡기지 않는다.
- 동일한 연락처(숫자 전화번호는 하이픈·공백 등 제거)를 제출한 참가자는 선택한 범위 내 최고 성공 기록만 순위에 반영한다. 닉네임이 같아도 연락처가 다르면 다른 사람으로 처리한다. 연락처를 입력하지 않는 경우 동일 참가자를 구별할 수 없어 각각 독립 도전으로 집계한다. 전화번호를 공유하는 참가자는 하나로 집계될 수 있고, 연락처의 실제 소유 여부는 확인하지 않는다. 경품 공정성을 위해 담당자가 중복 여부를 확인한다.
- 기존 V2 DB는 처음 실행할 때 자동 백업한 후 기존 기록을 1일차에 배정한다. 기록을 초기화하고 싶으면 관리자 기능을 사용한다. V2 백업에도 연락처가 있을 수 있으므로 보유 목적이 끝나면 백업 및 CSV도 삭제한다. 테스트 DB와 실물 DB는 기존대로 분리한다.

## 1. 설치 위치

ZIP 압축을 풀어 `exhibition_game` 폴더를 기존 저장소의 `robot/hilserl_시연수집/code/` 안으로 복사한다.

```
robot/hilserl_시연수집/code/

  teleop_test.py
  configs/flower_hil.json
  urdf/so101_new_calib.urdf
  exhibition_game/

    pad_mapper.ps1

```

Windows와 WSL에서 같은 폴더에 접근할 수 있도록 기존 Windows 드라이브(/mnt/c/...)에 둔다. Python GUI/Pygame은 필요 없다. Windows 웹 브라우저에 게임 화면이 뜬다.

## 2. Windows에서 ITB104 연결 (최초 1회)

- 패드를 PC USB에 꽂고 ANALOG 버튼을 눌러 아날로그 모드를 켠다. Win+R → joy.cpl → 장치 속성에서 두 스틱이 독립적으로 작동하는지 확인한다.
- 다른 게임패드는 분리한다. 게임패드는 WSL에 usbipd로 넘기지 않는다.
- PowerShell에서 `exhibition_game` 폴더로 이동한다(탐색기에서 폴더 주소창에 powershell 입력 가능).

```powershell
powershell -ExecutionPolicy Bypass -File .\pad_mapper.ps1
```

화면 안내에 따라 스틱/버튼을 하나씩 조작한다. `pad_map.json`이 만들어진다. 원래 팀 코드의 mapper를 복사했으므로 Y/A/X/B 등에 대응하는 1/3/4/2번 버튼도 매핑해야 하지만 게임 판정에는 쓰지 않는다. 축이 겹치거나 아날로그 확인이 실패하면 재실행한다. 기존 학습용 매핑을 덮어쓰지 않는다.

같은 창에서:

```powershell
powershell -ExecutionPolicy Bypass -File .\gamepad_sender.ps1 -Port 5567
```

창을 열어 둔다. WSL 게임이 아직 없으면 [대기]가 정상이다. 전시용 송신기는 만들어진 DirectInput 매핑만 사용한다(다른 XInput 패드 우선 연결 방지).

## 3. 로봇 없는 테스트 (권장)

WSL Ubuntu에서 같은 `exhibition_game` 폴더로 이동한 뒤:

```bash
python flower_game.py
```

Windows Chrome/Edge에서 `http://localhost:8091` 열기. 포트 5567(게임패드), 8091(게임 UI)은 기존 프로젝트의 5557/8080과 분리했다. WSL localhost 포워딩이 켜져 있어야 한다. 브라우저에서 도전 시작을 누르려면 스틱/버튼을 놓고 있어야 한다. 모의 모드의 점은 입력 확인용이며 물리 시뮬레이터나 자동 파지 판정은 아니다.

## 4. 실제 로봇 연결 (팀 담당자만)

기존 README의 연결/캘리브레이션 방법을 그대로 사용한다. 기존 AI 정책, 시연 수집, teleop 등 같은 모터 포트를 사용하는 프로그램을 모두 종료한다. 로봇 USB는 기존 방식으로 WSL에 붙이고, 게임패드는 Windows에 둔다. 기존 `attach_usb.ps1`, `setup_session.sh`의 장치/캘리브레이션 확인 방법을 참고한다. 게임은 카메라와 AI 모델이 없어도 된다. `conda activate lerobot` 및 기존 HIL 역기구학 환경 필요.

안전 설정 전에는 실물 실행을 거부한다. `safety.json`의 `workspace.min/max`를 전시 배치에서 측정한 안전한 말단 작업영역(m, x 앞/y 왼쪽/z 위)으로 채운다. 기존 flower_hil.json의 측정 상자 min [0.075,-0.278,-0.001], max [0.398,0.15,0.3] 이내에서 더 좁게 설정한다. 이 값은 전시 안전 범위가 아니다. `joint_limits`의 관절별 [최소,최대]도 실제 장비의 캘리브레이션 각도(도), 그리퍼는 0~100 단위에서 검증한 안전 범위를 직접 채운다. 임의로 숫자를 넣지 않는다. 테이블/화병/꽃과 다른 링크의 충돌 위험, 그리퍼 파지력, 모터 전류, 비상정지를 따로 검증하고 `verified: true`로 바꾼다. 실물 설정이 기존 URDF 및 원본 작업 상자를 벗어나면 실행을 거부한다.

팔을 안전한 시작 위치에 놓고 받칠 준비를 한 상태로 감독자가 실행:

```bash
conda activate lerobot
python flower_game.py --real --confirm-supervisor
```

기본 `/dev/ttyACM0`, `my_follower_arm`은 원본 설정을 읽는다. 다른 포트라면 `--robot-port /dev/ttyACM1`처럼 실제 확인된 포트로 지정한다. 시작 시 기존 teleop_test의 sync_goal_to_present 및 기존 WristEEController를 재사용한다. 자동 시작 자세 이동/복귀는 하지 않는다. 기존 캘리브레이션 필요. 기본 20Hz, 최대 말단 명령 이동 4cm/s(2mm/스텝), 회전 16도/s, 그리퍼 20단위/s. 실제 속도/힘 보장은 아니며 저속으로 점검해야 한다. IK 숙임은 시작 자세의 pitch로 고정. 작업 범위와 각도 제한, 목표 대비 실제 위치 오차 검사로 불가능한 명령을 차단한다. 모터의 자체 위치 제어는 남으므로 소프트웨어 정지는 토크 차단이 아니다.

## 5. 전시 진행

참가자는 닉네임(1~16자)과 연락처(선택, 동의 필요)를 입력한다. 진행자가 로봇과 꽃 배치를 확인한 뒤 도전 시작 → 3, 2, 1, START! → 카운트업(0~60초). 카운트다운 동안 이동 명령은 보내지 않는다. 꽃을 안정적으로 잡으면 진행자가 성공 판정 버튼을 누른다. 60초 이내 성공만 TOP 3에 올라간다. 동일한 연락처 기준으로 최고 기록을 집계한다. 연락처가 없는 도전은 독립 기록이다. 동률(밀리초 기준)은 먼저 등록한 기록이 앞에 표시된다. 다음 참가자 버튼은 게임 상태만 초기화하며 로봇을 이동시키지 않는다. 로봇 위치는 팀원이 안전한 방법으로 수동 복구한다.

오른쪽 상단 그림은 실제 수신한 스틱과 매핑된 버튼을 강조하고 해당 입력의 기능을 표시한다. 방향키/ANALOG 자체는 기존 매핑 송신기에 포함되지 않아 실시간 강조하지 않는다. START 버튼은 참가 등록을 건너뛰지 않도록 게임 시작에 사용하지 않는다. 화면의 도전 시작을 클릭한다.

### 기록 및 연락처 관리

- 공개 화면/API에는 닉네임과 성공 시간만 표시한다. 참가자 동의가 있을 때만 연락처를 저장한다(선택 항목). 연락처 입력 필드는 참가 시작 후 초기화한다.
- 기본 DB는 `~/.local/share/kkotsooni_game/` 아래에 저장된다. UI 테스트는 `ui_test.sqlite3`, 게임패드 모의 모드는 `demo.sqlite3`, 실제 로봇은 `real.sqlite3`. 프로그램을 종료해도 기록이 남는다. `--db`로 파일을 지정하면 모드별 분리가 적용되지 않으므로 주의한다.
- 연락처는 암호화되지 않은 로컬 DB에 저장된다. 전시 담당자만 PC 계정/파일에 접근하도록 하고, 공개 화면에 연락처가 포함된 파일을 열지 않는다. 참가자에게 실제 수집 목적(예: 경품 안내), 이용 및 보유 기간, 삭제 방법을 명확히 안내하고 목적 달성 후 개인정보를 삭제한다. 연락처가 필요하지 않으면 수집하지 않는다.
- 실제 기록을 담당자용 CSV로 내보내려면 게임을 종료한 뒤 다음 명령을 사용한다(새 파일 이름 사용, 기존 파일 덮어쓰기 방지):

```bash
python flower_game.py --real --confirm-supervisor --export-private private_results.csv
```

CSV와 DB는 GitHub에 올리거나 공유하지 않는다. 모의 기록은 `--real --confirm-supervisor`를 생략하고, UI 테스트 기록은 `--ui-test`를 지정한다. 기록 초기화와 개별 삭제는 V3의 관리자 설정을 사용한다. 데이터베이스에는 참가자 구분용 연락처 기반 키도 저장되므로 단순히 contact 열만 비우는 방식으로 개인정보를 삭제했다고 볼 수 없다. 경품 안내 목적이 끝나면 담당자가 필요한 익명 통계만 별도로 남긴 뒤 전체 기록, 백업 및 CSV를 삭제한다. 관리 기능은 실행 중인 게임을 중단시키지는 않으며 게임 종료 상태에서만 사용할 수 있다.

- 왼쪽 스틱: 앞뒤/좌우 (말단 위치)
- 오른쪽 스틱: 높이/손목 회전
- L2 열기, R2 닫기, R1 조작 허용, SELECT 정지
- 스틱/버튼을 놓은 상태에서 시작. R1을 놓으면 새 이동 명령 중단. 다시 조작하려면 스틱도 놓고 R1을 누른다.
- 패드 통신 끊김(0.2초 수신 제한), 브라우저 heartbeat 끊김(0.7초), SELECT/진행자 정지, 시간초과 시 새 이동 명령 중단. 통신/IK가 지연될 경우 실제 정지까지 더 걸릴 수 있다. 하드웨어 비상정지와 물리적 접근 차단 필수. 로봇 전원 차단 시 팔이 떨어질 수 있으므로 안전 지지 필요.
- 프로그램 종료: WSL Ctrl+C, PowerShell Ctrl+C. 실물은 기존 설정대로 마지막 자세 유지. 전원 분리는 담당자가 수행한다.

## 6. 검증 범위

V3 Python 단위 테스트 10개 통과(기존 타이머, 정지, 입력 처리 및 새 일차/참가자 구분/관리 기능/DB 마이그레이션). JavaScript 문법 검사 통과. Chromium에서 실제 Python HTTP 서버 요청을 테스트용 브리지로 연결해 1일차와 2일차 게임, 조회 탭과 등록 일차 분리, 잘못된 PIN 거부, CSV 다운로드, 날짜별 삭제를 검증했다. 테스트 환경의 브라우저 직접 localhost 접근은 차단되어 일반 브라우저 직접 연결은 현장에서 확인해야 한다. 기존 게임패드 매핑·송신 및 실물 제어 코드는 변경하지 않았다. 실제 ITB104, Windows/WSL 연결, 실물 SO-101/LeRobot/캘리브레이션 및 물리적 안전은 전시 전 담당자가 반드시 현장에서 검증한다. 이 코드는 안전 인증된 제어 장치가 아니다.
